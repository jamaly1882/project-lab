# إدارة المستخدمين والمديريات

هذه الميزة تسمح لمدير النظام بإنشاء حسابات المستخدمين من داخل **لوحة التحكم**،
وتحديد **مديرية** و**دور وظيفي** لكل مستخدم من لوحة الإدارة، وعند تسجيل دخوله
تظهر له بيانات مديريته وأيقونة الدور المحدد فقط.

---

## 1) الخطوات من داخل النظام

1. سجّل الدخول بحساب مدير النظام (`superuser` أو `staff`).
2. افتح **لوحة التحكم** (`/index/`).
3. من القائمة الجانبية اختر **👥 المستخدمون والصلاحيات ← إضافة مستخدم**
   أو اذهب مباشرة إلى: `/accounts/users/`.

في الصفحة ستجد:

| الحقل | الوصف |
|------|--------|
| اسم المستخدم | مطلوب، بالإنجليزية، ولا يقبل التكرار |
| كلمة المرور + تأكيدها | مطلوبتان (6 أحرف على الأقل) |
| **المديرية** | مطلوبة، تُقرأ من جدول `mahfth` |
| **الدور** | مطلوب: رئيس قسم مساحة، مهندس مساحة، أو منسق قسم مساحة |
| رقم الهاتف | اختياري |
| الاسم الأول / الأخير / البريد | اختيارية |

أسفل النموذج جدول بكل المستخدمين مع أزرار:

* **تعديل** — لتغيير الاسم أو المديرية أو الدور أو تعيين كلمة مرور جديدة.
* **تعطيل / تفعيل** — لإيقاف الحساب مؤقتاً دون حذفه.
* **حذف** — لحذف الحساب نهائياً (لا يمكن حذف حسابك الحالي أو آخر مدير للنظام).

---

## 2) ماذا يحدث عند تسجيل دخول المستخدم؟

* **مدير النظام** (`is_superuser` أو `is_staff`) يرى **كل** المديريات والبيانات ولوحة الإدارة.
* **المستخدم العادي** يرى **مديريته فقط**، وتحدد صلاحية الدور الأيقونات المتاحة له:
  * رئيس قسم مساحة ← يُحوّل مباشرة إلى ملف رئيس القسم، دون عرض أيقونة اختيار الدور.
  * مهندس مساحة ← يُحوّل مباشرة إلى ملف المهندس، دون عرض أيقونة اختيار الدور.
  * منسق قسم مساحة ← تظهر له روابط إصدار التقريرين بغرض البناء والاستشارة.
  * إصدار التقريرين مسموح لمنسق القسم ومدير النظام فقط.
  * الأدوار الثلاثة لا تستطيع فتح أيقونة «إدارة المساحة» أو صفحاتها المرتبطة، حتى عند محاولة فتح الرابط مباشرة.

  * لوحة التحكم تعرض اسم مديريته وإحصائياتها وآخر طلباتها.
  * قوائم «المديرية» في نموذج إدخال البيانات تحتوي مديريته فقط.
  * كل عدادات الطلبات والتقارير والإشعارات (AJAX) مقيّدة بمديريته.
  * نتائج البحث السريع (live search) لا تُظهر بيانات مديريات أخرى.
  * حتى لو حاول إرسال `id` مديرية أخرى من أدوات المتصفح، يُحفظ الطلب
    على **مديريته** تلقائياً.

> إذا كان حساب المستخدم غير مرتبط بأي مديرية، فلن يرى أي بيانات،
> وتظهر له رسالة تطلب مراجعة مدير النظام.

---

## 3) أين تُحفظ المديرية؟

أُضيف حقل جديد `mahfth` في جدول `accounts.Profile`:

```python
class Profile(models.Model):
    user = models.OneToOneField(User, ...)
    city = models.ForeignKey('City', ...)        # الحقل القديم
    phone_number = models.CharField(max_length=100)
    mahfth = models.ForeignKey('masha.Mahfth',   # ← الجديد
                               related_name='user_profile_mahfth',
                               null=True, blank=True,
                               on_delete=models.SET_NULL,
                               verbose_name='المديرية')
```

كذلك أُضيف حقل `mahfth` إلى جدول `accounts.City` ليتوافق مع البيانات القديمة،
وقواعد تحديد المديرية تعمل بالترتيب التالي:

1. `Profile.mahfth`  (الأولوية)
2. `Profile.city.mahfth`  (للتوافق مع البيانات السابقة)

## 4) لوحة إدارة Django

يمكن أيضاً إدارة المستخدمين من `/admin/`:

* `auth.User` أصبح يعرض عمود **المديرية** وفلتر حسب المديرية.
* داخل صفحة المستخدم يوجد قسم **ملف المستخدم (المديرية والهاتف)** لتحديد المديرية مباشرة.

## 5) تطبيق التغييرات

```bash
python manage.py migrate
```

سيتم تطبيق الترحيلات الجديدة:

* `accounts/migrations/0004_...` — إضافة حقول المديرية.
* `masha/migrations/0045_...` — تحديثات متأخرة عن تعريفات الموديلات.

> **ملاحظة:** تم إصلاح ترحيل قديم (`masha/migrations/0008_form_sent_att.py`)
> كان يمنع إنشاء قاعدة بيانات جديدة (`default=1` في حقل تاريخ). الآن
> `python manage.py migrate` يعمل على قاعدة بيانات فارغة بدون أخطاء.

## 7) المسارات الجديدة

| المسار | الاسم | الوظيفة |
|--------|------|---------|
| `/accounts/users/` | `accounts:user_manage` | القائمة + نموذج الإضافة |
| `/accounts/users/<id>/edit/` | `accounts:user_edit` | تعديل مستخدم |
| `/accounts/users/<id>/toggle/` | `accounts:user_toggle_active` | تعطيل/تفعيل (POST) |
| `/accounts/users/<id>/delete/` | `accounts:user_delete` | حذف (POST) |

كل هذه المسارات محمية: تُعيد توجيه أي مستخدم غير مدير إلى صفحة الدخول.

## 8) إصلاحات: صفحة الدخول وروابط المدينة/المديرية

### 8.1) صفحة الدخول كانت تظهر بدون حقول

**المشكلة:** عند فتح `/accounts/login` (بدون شرطة أخيرة) كان يعمل مسار
`django.contrib.auth.urls` الافتراضي الذي يعرض قالب
`registration/login.html` **بدون تمرير `form`**، فتظهر البطاقة الزرقاء
بعنوانها وزر الدخول فقط — بدون حقلي «اسم المستخدم» و«كلمة المرور».

**الإصلاح:**

| الملف | التغيير |
|------|---------|
| `erea/urls.py` | تقديم `accounts.urls` قبل `django.contrib.auth.urls` |
| `accounts/urls.py` | `login/` + مسار بديل `login` (بدون شرطة) للروابط القديمة |
| `accounts/form.py` | إضافة `LoginForm` (AuthenticationForm) بتسميات عربية |
| `accounts/views.py` | تمرير `LoginForm` دائماً + رسالة خطأ عربية + رفض الحساب المعطّل |
| `accounts/templates/registration/login.html` | تنسيق حقول واضح على البطاقة الزرقاء |

النتيجة: `/accounts/login/` و`/accounts/login` كلاهما يعرض حقلي الدخول،
وبعد الدخول الناجح يذهب المستخدم ذو الدور المساحي مباشرة إلى شاشة قسم المساحة؛ وبقية المستخدمين إلى لوحة التحكم `/index/`.

### 8.2) روابط الأقسام تتبع مدينة المستخدم

**المشكلة:** القوالب كانت تقارن المديرية بـ `zz.profile.city.city`:

```django
{% if i.name == zz.profile.city.city %}
```

فإذا لم تُسجَّل للمستخدم **مدينة** (وهو الحال الافتراضي، لأن الحقل اختياري)
تصبح قائمة المديريات **فارغة**، ولا تظهر أي روابط/بيانات.

**الإصلاح:**

* `masha/scoping.py`:
  * `get_user_city()` — كائن المدينة من `Profile.city`.
  * `get_user_city_name()` — اسم المدينة، وإن لم توجد يُستخدم اسم المديرية.
* `accounts/context_processors.py` — إتاحة `my_city_name` و`user_city`
  و`my_scope_name` و`is_system_manager` في كل القوالب.
* القوالب (`astshr.html`، `enter_data_report_masahi.html`،
  `enter_face_enter_nah.html`) — تعرض مديرية المستخدم فقط دون الحاجة
  لتسجيل مدينة، وتُظهر عدّاد الطلبات الصحيح.
* `masha/templates/masha/interface.html` — بطاقات الأقسام
  (ادارة المساحة / قسم المساحة) تظهر فقط لمن لديه مدينة/مديرية،
  وشارة «المدينة: …» أعلى الصفحة.
* `masha/templates/masha/index.html` — بطاقة لوحة التحكم تعرض المدينة
  والمديرية معاً.

### 8.3) صلاحيات شاشات الأقسام

سابقاً كانت شاشات الأقسام تتطلب صلاحيات Django مثل
`masha.add_form` / `masha.add_unit`، فكان المستخدم العادي يُرفض رغم أن
روابط مدينته تظهر له.

أُضيف في `masha/views.py`:

```python
def can_access_mahfth_screen(user):
    return is_manager(user) or _user_in_scope(user)

def mahfth_screen_required(view_func): ...
```

* مدير النظام ← كل الشاشات.
* مستخدم مرتبط بمدينة/مديرية ← شاشات قسمه، والبيانات مقيّدة بـ`scoping.py`.
* مستخدم بلا مدينة/مديرية ← لوحة التحكم مع رسالة
  «لم يتم ربط حسابك بأي مدينة أو مديرية بعد».

### 8.4) تعيين الدور للمستخدم من لوحة التحكم

استُبدل اختيار **المدينة** في نموذجي الإضافة والتعديل بقائمة **الدور**،
ويظهر الدور في جدول المستخدمين بصفحة `/accounts/users/`. يظل حقل المدينة القديم
في قاعدة البيانات للتوافق مع المستخدمين السابقين، لكنه لم يعد جزءاً من نموذج الإدارة.

### 8.5) تعيين الأدوار المساحية

يُحفظ الدور في الحقل `Profile.role`، ويظهر كقائمة منسدلة بدلاً من اختيار المدينة في نماذج الإضافة والتعديل.
الأدوار المتاحة هي: رئيس قسم مساحة، مهندس مساحة، ومنسق قسم مساحة. يُوجّه رئيس القسم والمهندس مباشرة إلى ملف كلٍ منهما دون عرض أيقونة اختيار الدور، بينما تظهر للمنسق روابط إصدار تقريري البناء والاستشارة. تُحجب أيقونة إدارة المساحة والروابط التابعة لها عن الأدوار الثلاثة.
